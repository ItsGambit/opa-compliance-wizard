5.49.0 — **Local installs can upgrade themselves with a guided, signature-verified command; computers without internet get an offline bundle; early testers can opt in to a prerelease channel. Existing installs keep working exactly as before with no action.**
A minor release. Nothing is checked, downloaded or installed unless you run it. The new local-mode command and the offline bundle are the command-line half; the buttons for them in the Updates page arrive with the in-app flow.
- **Added.** `python launch.py upgrade` for local (laptop or desktop) installs on Windows, macOS and Linux: `--check`, `--to X.Y.Z`, `--from-file`, `--restore-previous` (with `--restore-data`), `--discard-previous`, `--status`, `--channel`, `--confirm` for scripts. It downloads the signed release, **verifies the signature, the signed manifest and the version against the keys pinned in your install before unpacking anything**, unpacks into a sibling folder `<your folder>-<version>`, builds its Python environment from the hash-pinned `requirements.lock`, shows what changes (including database migrations and whether they are rollback-safe), asks you to **type the version** (local mode has no sign-in, so there is no MFA and none is faked), copies your data, swaps the folder names (the old folder is kept as `<your folder>-previous`) and starts the new code once to check it; if that fails the previous folder is put back automatically. Exit codes: 0 ok, 1 newer release found (`--check`), 2 refused, 3 failed and nothing changed or everything put back, 4 failed and you must act. Upgrades are recorded in the new folder's Audit Log (`upgrade.local_completed`, `upgrade.local_restored`; refusals as `upgrade.verify_failed` / `upgrade.local_failed` in the old one).
- **Added.** What is carried over, exactly: `audit_store.db` (copied with SQLite's online backup and integrity-checked, so a half-written page can never be copied), `environments.json` and its backups, `audit_log.jsonl`, `banner_config.json`, `access_control.json`, `secrets_log_cache.json`, `update_check.json`, `release_keys.local.json`, `.env`, saved folder templates and `folders_result_*.csv`, with their file permissions. Everything is copied, never moved. Credentials in the operating system keychain are not touched. Other files in the old folder are listed and left there.
- **Added.** Restoring: `--restore-previous` (typed `RESTORE`) swaps the folders back; the folder it replaces is kept as `<your folder>-replaced-<version>`. By default it is code only and your current data stays; it is refused, with the reason, when a migration the newer version made is not rollback-safe, and `--restore-data` then brings back the previous folder's own older data instead. An upgrade interrupted by a power cut is repaired by running `--restore-previous` from the previous folder.
- **Added.** The offline bundle: `tools/release.py build-offline` produces `ocw-<version>-offline.tar.gz` (and a `.sha256`): the signed release unchanged plus hash-pinned wheels for Python 3.9 to 3.14 on Linux (x86-64, ARM), macOS (Apple silicon, Intel) and Windows. Install it with `python launch.py upgrade --from-file` (local) or `server/deploy.sh --release X --from-dir DIR` (servers on the in-place layout); packages are installed with `pip install --no-index --require-hashes --only-binary=:all:`. The bundle needs no signature of its own: the release inside is verified like any other and pip refuses any package whose sha256 the signed `requirements.lock` does not record.
- **Added.** A prerelease channel, off by default: `python -m server.updater set-channel prerelease|stable`, `OPA_UPDATE_CHANNEL`, `upgrade --channel` for one run, and `{"channel": "stable"|"prerelease"}` on `POST /api/upgrade/settings` (`channel` and `channel_source` also in `GET /api/upgrade/status`, and `latest.prerelease`). The prerelease channel reads the list of releases and offers the newest of either kind; every release is still verified against the same pinned keys. `OPA_RELEASE_LIST_URL` names the list endpoint of a mirror. Changing the channel is audited (`upgrade.settings`).
- **Added.** `python -m server.updater share-version on|off`: the existing opt-in that adds the installed version to the update check's User-Agent (off by default) now has a command-line switch; `status` shows it.
- **Changed.** The release unpacker (used by `deploy.sh --release`, the updater's staging and the local upgrade) now also refuses Windows device names (`CON`, `NUL`, `COM1` ...), names with `:` or trailing dots or spaces, and names that differ only by letter case, so a release unpacks identically on every operating system.
- **Changed.** The update check reads release data through one shared parser; a stored channel that is not `stable` or `prerelease` is treated as `stable`.
- **Security.** Verification always precedes unpacking; the archive is unpacked with regular files and folders only (links, hard links, devices, absolute or `..` paths and unlisted files are refused) and each file is hashed against the signed manifest; the offline bundle's outer archive is unpacked with a fixed set of member names, size caps and no links. The guided upgrade never deletes before the new version has started, never replaces an existing folder it did not create, never follows a symbolic link for your data (it refuses), and the Windows hand-over file is used only if it names exactly this install's folders and was not writable by other users. The dashboard process is only stopped when it is this folder's own, and only after you agree.
- **Privacy.** Unchanged: the check sends one HTTPS request to the release host and nothing about your tenant, users or data; the installed version is sent only if you opt in. The upgrade downloads the release files from the release host (or a mirror you configure) and sends nothing else.
- **Known limitations.** (1) **Not run on real Windows:** the folder-rename retries, the hand-over between the two launcher processes and the path-length check are covered by tests that simulate Windows; try an upgrade on a throwaway Windows install before relying on it. (2) The previous folder keeps its own copy of your plain-text settings (`.env`, `environments.json`) until you run `--discard-previous`. (3) A folder that is a git checkout is replaced by a plain release folder (the old one, with its `.git`, is kept as `-previous`). (4) The offline bundle does not cover Alpine/musl Linux or 32-bit systems, and a server on the 5.47.0 upgrade layout cannot yet install packages from it (the updater stages only the release); `deploy.sh` says so and changes nothing. (5) The Updates page has no buttons for the local upgrade, the restore or the channel yet (API and command line only). (6) Not scheduled: a laptop may be asleep. (7) `build-offline` needs the internet and `packaging` on the maintainer's computer and has been tested with a stand-in for `pip download` only.
